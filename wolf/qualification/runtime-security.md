# Runtime dependency security and image provenance

## Meaning

This records the targeted 13 November 2026 security maintenance of the Kener 4.1.9 fork, the compatibility evidence for its changed dependencies, and the revision-labelled build route. The source preserves supported status, monitoring, notification, backend, image-upload and private composer behavior. Residual advisory conditions remain explicit; a smaller audit count is not a whole-product security verdict. Source qualification, actual image identity, recoverable artifact admission and live rollout are separate facts.

## Dependency selection

The starting source is `c4c33cbbebd0e92ab48c2f0db3651c4d8b805c2e`. Its production-lock observation reported 42 affected package names, including conditional and inherited findings. The selection updates those affected paths rather than running an unrestricted dependency upgrade or changing Kener's upstream release.

- SvelteKit **2.70.4**, adapter-node **5.5.8**, Svelte **5.57.3**, devalue **5.9.4** and DOMPurify **3.4.17** update compiled request, serialization and sanitization code. Build-time declarations do not make that code irrelevant to production. The [Accept-header advisory](https://github.com/sveltejs/kit/security/advisories/GHSA-29g2-3rmr-qm68) is patched in 2.70.2; this candidate retains SvelteKit 2 rather than selecting an unrelated framework migration.
- Axios **1.21.1**, follow-redirects and form-data fixes retain native HTTP monitoring, configured redirects and proxy support. [Proxy-to-direct redirect leakage](https://github.com/axios/axios/security/advisories/GHSA-j5f8-grm9-p9fc) is a real consequence for supported proxy configurations. HTTP/2-specific findings did not establish that Kener used HTTP/2.
- Sharp **0.35.5** changes the native prebuilt decoder and libvips dependencies. The [maintainer's advisory](https://github.com/lovell/sharp/security/advisories/GHSA-f88m-g3jw-g9cj) affects untrusted decoding, which Kener performs for authenticated image uploads. Removing formats or relying only on a successful module import would not preserve and qualify the supported upload behavior.
- Nodemailer **10.5.0**, mailparser **3.14.3** and Resend **6.38.0** update the supported notification path and its parsers. Nodemailer's [release history](https://github.com/nodemailer/nodemailer/blob/v10.5.0/CHANGELOG.md) retains the SMTP transport API and dual ESM/CommonJS entry points; its Node 20 minimum fits Kener's Node 24 requirement. Local SMTP composition, acceptance and recipient refusal need direct qualification; provider credentials and actual delivery are outside this evidence.
- gRPC **1.14.7**, mysql2 **3.24.6**, BullMQ **5.81.5**, gamedig **5.3.3**, undici **7.30.2**, nanoid **5.1.16** and affected parser/utility dependencies receive targeted compatible updates. Existing global overrides are advanced for their security fixes. Glob **14.0.6** and minimatch **11.0.8** retain the translation-script glob APIs; esbuild **0.28.2** and Vite **7.3.8** update the existing build tools. No development server is added to the production entry.

Versions and engine/license metadata were read from the primary npm registry on 13 November. The lockfile records exact integrity hashes. Existing packages and supported product paths remain; no new direct dependency, schema, API shape, authentication rule, scheduler or CI workflow is introduced.

## Residual production findings

The refreshed `npm audit --package-lock-only --ignore-scripts --omit=dev --json` reports **eight low**, **zero moderate**, **zero high**, **zero critical** package findings. These are package-level and inherited records, not eight independently demonstrated exploits. [The exact dated report and 168 changed lock resolutions](runtime-dependencies-audit.json) are preserved alongside this record. The complete builder report is **17** (11 low, six moderate, no high or critical). Its additional moderate findings concern Vitest's test-server/mock interfaces and the typography build plugin's selector parser; neither starts a corresponding service in the production entry. This does not qualify those developer interfaces for untrusted access.

SvelteKit 2 still carries [enhanced-form untrusted redirection](https://github.com/sveltejs/kit/security/advisories/GHSA-pfhg-q3qv-9q6r), whose maintainer selects 3.0.0 as the fix. The npm report also lists [prerendered cache-control XSS](https://github.com/sveltejs/kit/security/advisories/GHSA-27mw-82g8-phjj) as affecting all versions below 3, while the current maintainer advisory says it is patched in **2.70.4**, the exact selected version. That source disagreement is preserved rather than forcing an unnecessary major upgrade or claiming a zero-finding audit.

Deepmerge **4.3.1** has no patched release in the observed registry. Its prototype-poisoning finding propagates through Svelte tooling, bits-ui/runed/svelte-toolbelt and the Scalar consumer. Installed presence alone establishes neither attacker-controlled merge input nor absence of such a path. No complete bundle call graph or adversarial exploit qualification is claimed. These residual conditions return for release judgment; this candidate does not remove UI, documentation or notification capabilities to eliminate names from a report.

## Build provenance

`node wolf/build-image.mjs --tag <local-tag>` verifies its exact Git root, obtains the clean Git revision and invokes the existing multi-stage Dockerfile. A lost worktree Git marker cannot silently select a parent repository's revision. The final image carries `org.opencontainers.image.revision` and `org.opencontainers.image.source`. Missing or malformed direct `SOURCE_REVISION` values refuse the build. Dirty-context and parent-repository refusals were exercised before any Docker invocation. Manual arbitrary revision input is not authenticated provenance; the helper binds the ordinary route to its actual checkout.

This label repairs a concrete downstream materialization requirement. It does not authenticate the builder, make builds reproducible, measure an archive or ciphertext, prove lost-host recovery, or authorize an image tag/publication/deployment effect. Old image and recovery identities remain unchanged.

## Qualification

The supported source checks ran in the existing isolated Playwright 1.61.1 Linux container, Node **24.17.0**, UTC, with two CPU cores and at most 3GiB memory. `npm run check` completed with **zero errors and zero warnings**, including the final added transport test. `npm test -- --maxWorkers=2` passed **71 files / 808 tests**, with eight declared skips. After adding the actual HTTP-adapter test, the focused HTTP/SMTP run passed **four tests**; the rest of the suite's inputs and dependency bytes were unchanged. Chromium tests ran headlessly in the isolated container.

The HTTP fixture exercises real Axios redirects on/off and distinguishes connection loss from an observed failed response. The SMTP fixture exercises the production transport against a loopback-only server, retaining MIME composition, server acceptance and recipient rejection. Neither uses actual recipients, credentials or provider services. The only SMTP source change is the named `TransportOptions` import required by Nodemailer 10's types; runtime options remain unchanged.

The write-parity/image tests passed **47 cases** on each of PostgreSQL 16 and MariaDB 11, and the current-status/dashboard/group tests passed **40 more cases** on each engine, all using harmless disposable state. Each fixture recorded all **33 migrations**. The first combined PostgreSQL invocation failed because the existing test groups use different migration-name representations (bare filenames versus `/migrations/` paths). Running those groups against separate empty fixture databases resolved the test-input collision without changing product migrations, schema or test behavior. SQLite and Chromium are covered by the full repository run. These source backend results are not image-level PostgreSQL/MySQL startup or restored-production evidence.

The brand pin/byte check and all **nine** dependency-free brand/notification-reader tests passed. The first workstation lock-only attempt correctly refused Node 26 through the existing engine policy; lock resolution then used the selected **Node 24.22.3** container. No machine runtime was installed or reconfigured. All bulk dependency/cache/fixture work uses the D-backed Docker store or this contribution's D working paths. Whole-host instantaneous peak and recording impact were not measured.

The exact changed-source image, actual Node/native/startup results, labels, export identities and final resource disposition belong to the build receipt returned with the candidate. This source record does not imply an image, archive admission, encryption footprint, source acceptance, hosted CI, publication, deployment, protected recovery or human receipt. Alpine and docs-enabled production images require their own evidence when selected; this contribution targets the existing Debian/docs-off operating variant.
