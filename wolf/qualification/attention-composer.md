# Operated attention composer

## Meaning

This patch joins one operator-owned, pure JavaScript composer to native alert dispatch, repeated evaluation and the existing webhook sender. An additive application-database table retains due-event claims, submission outcomes, operating facts and reconciliation. This document owns the opt-in source/runtime contract and its qualification limits. Source tests are not deployment or recipient evidence.

## Opt in deliberately

With no `KENER_ATTENTION_CONFIG`, normal Kener behavior is unchanged. When configured, this absolute JSON path contains `version: 1`, a finite array of actual numeric `triggerIds`, and `composer`/`declaration` objects each containing an absolute `path` and a lower-case SHA-256 `sha256`. The files are operator-owned and mounted read-only. They are not vendored into this public repository or the image. A changed or unavailable operated input refuses selected dispatch; it never falls back to a sentence in a stored template.

The module exports `validateDeclaration(declaration)` and `composeKener(declaration, variables, now, incidentFacts)`. It has no runtime dependency on Kener or filesystem effects. Composition returns `{text, row, notification: {event, standing, next}}`; `event: null` means no send. The existing alert variable contract supplies identity/confirmation/transition and explicitly unavailable onset. The sender supplies current operating facts plus retained messages. A due event remains due until the native sender obtains a useful submission receipt.

The first qualified channel is the already-configured HTTPS Telegram `sendMessage` webhook. The native sender preserves its recipient/routing envelope, replaces `text` with JSON-encoded plain composer output, and removes old parse-mode/entities. Template expansion and environment substitution never interpret composed text. Other channel contracts are not guessed. Status DOWN and NO_DATA are supported, and NO_DATA always composes missing observation rather than service failure/recovery. There is no new sender, scheduler, private-source dependency or dashboard.

## State and operator contract

`alert_notification_state` belongs to the same database and protection boundary as its native alert/trigger. The composite key is `(alert_id, trigger_id)`; optimistic `revision` protects updates. It retains facts, their attributable reference, and distinct attempted `sending`, `sent`, HTTP `accepted`, `unknown` and `failed` outcomes. A committed claim precedes HTTP. A process loss or unclassified response holds retry, including recovery, until reconciled. A successful Telegram response must contain a Message matching the sent recipient and text; it proves submission, not phone or human receipt. HTTP diagnostic JSONL remains separate.

The existing `/api/v4` bearer hook protects `/api/v4/attention/<alert_id>/<trigger_id>`:

- GET reads this native relationship and its state, or null before first use. Persisted state remains readable and correctable even if the current binding, composer or declaration is missing/broken. An intact native alert/trigger relationship and the existing bearer authentication are still required. GET/PATCH do not load executable artifacts; POST and dispatch still verify all operated pins and refuse new sends when unavailable.
- PATCH `action: facts`, `revision`, `reference` and `facts` partially updates actual pickup/changed custody and observed classification. Omitted fields retain their values. `null` clears `failureKind`, `reason` or `endedBy`; `pickup: null` clears the pickup. Changing `failureKind` without supplying `reason` clears the previous custom reason, returning to declared wording. Pickup requires who, since, Session and current standing; absence of knowledge is distinct from known no-pickup. A retained pickup with `pickupKnown: false`, or `endedBy` with `endedOnItsOwn: true`, refuses atomically; clear the contradictory field in the same PATCH. Pickup/fact edits do not send.
- PATCH `action: reconcile`, `revision`, `reference`, exact `attempt`, `outcome: sent|failed`, and `at` for a successful submission preserves the attempted event and records explicit evidence. It does not send.
- POST `action: evaluate` plus current `revision` invokes the same native sender, including a held recovery after reconciliation. Read after any interrupted effect before retrying.
- PATCH `action: retry`, current `revision` and an attributable `reference` rearms a known rejected delivery after a coworker corrects its cause. It preserves receipts, does not send, and refuses while any attempt is sending/accepted/unknown. Subsequent evaluation uses the same composer, claims and sender.

Adapters that project this native API must retain the finite `retry` fields (`key`, `attempts`, `nextAt`, `exhausted`), `retryReference`, message `retryAfterSeconds` and the `telegram-rejection` boundary, and admit the explicit `retry` action. An older adapter's successful read does not establish that it exposes retry standing or can rearm delivery. Native API qualification and external adapter adoption remain separate.

### Rejection, ambiguity and durable retry

Only a parsed Telegram `ok: false` response with a 4xx `error_code`, description and no Message establishes a retryable rejection, marked `boundary: telegram-rejection`. HTTP status alone never proves no effect. Server 5xx, transport interruption and response-body read failure remain unknown/held even if the request may have reached Telegram. Unqualified 2xx remains accepted/held. Historical `failed` receipts without `telegram-rejection` or explicit `operator` proof are also held: the earlier source could mark a server error failed. Their original receipt survives; an attributable exact-attempt reconciliation can establish no effect. This conservative distinction applies to opted-in delivery state; ordinary triggers and their HTTP-only diagnostic format retain their existing contract.

Automatic delivery has four attempts per due event/standing/impact: the initial attempt and retries after **1, 5 and 30 minutes** from observation of each proven rejection, honoring a longer Telegram `retry_after`. Monitor samples and explicit Evaluate respect the persisted due time/budget. Exhaustion remains visible as `retry.exhausted: true`, without discarding the due event; the capable operator can correct and rearm it. Unrelated fact edits do not reset a delivery budget; a changed event/standing/impact is a distinct composer decision. Each automatic episode retains at most four receipts for the same unchanged event; deliberate operator rearm retains the earlier receipts and its reference.

The existing ten-second application scheduler queries indexed `next_retry_at` rows and invokes the same sender for due retries, including alerts already `RESOLVED`; no additional scheduler/service or healthy monitor sample is required. JSON `retry` is authoritative and its indexed due projection is saved in the same compare-and-swap as the receipt claim/completion. A committed sending claim clears the projection before HTTP. Thus a process interruption holds rather than blindly retries. The additive retry migration preserves existing receipts and resumes older proven-no-effect failures once; it leaves uncertain/sending/accepted and unqualified historical failures unarmed. Inactive alert configurations and disabled/detached/unselected triggers do not send. These source-selected timing/budget choices require operating judgment before live adoption; they do not alter the composer's down/follow-up/recovery policy.

This is an operator capability. Authentication does not itself grant effect authority. New API shapes and the additive state migration are source changes; prior databases/images cannot be treated as interchangeable recovery points. Retain valued receipts/configuration pins when rolling source back; dropping the table would erase duplicate/uncertainty knowledge. Its lifecycle follows the native alert/trigger, including cascade retirement. Existing unrelated histories, associations and incident behavior are preserved.

Its final native cases passed 15/15 on SQLite, PostgreSQL and MariaDB. MySQL exposed a fixture-only ISO-string datetime incompatibility, corrected to common UTC SQL datetime representation. These are local native/source results, with no hosted CI or live/provider effect implied. External API adapter retry projection/action adoption remains separate.
