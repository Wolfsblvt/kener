# Authentication state admission qualification

## Meaning

This record qualifies the server-side authentication admission repair following the 4.1.10 fork replay at `88b428e95d664e9b8d1b523df31696db81df3466`. It covers direct first-owner signup and the demonstrated subscriber, OIDC and invitation mutation order. The unchanged upstream fail-closed accessor remains the cryptographic boundary; the repair prevents missing configuration from leaving durable authority before that accessor is reached. It does not accept a release or establish any deployment's configuration or exposure.

## Source boundary

The existing setup predicate now uses the common authentication-configuration query. Both named sign-in actions check the required signing-key configuration before reading form data, querying users or setting cookies. A missing key returns HTTP 503 with the existing error/values form shape and blank values. Other setup conditions remain the UI's existing responsibility: a valid-key direct action still works when development infers `ORIGIN`. Subscriber OTP verification, OIDC creation and profile/role synchronization, and invitation creation invoke the common required-configuration guard before their writes. The guard delegates to the unchanged required-secret accessor and returns no secret value to its callers.

Missing and empty signing keys have the same refusal. Configured-key account creation, login, subscriber activation, OIDC synchronization, invitations, JWT signatures and API-key HMACs retain their existing behavior. Published example values are still warnings rather than a new quality gate. No fallback, schema, dependency, API-v4 shape, authentication redesign or runtime configuration change is introduced.

The bounded caller inspection found API-key creation already hashes before insertion; forgot-password, verification and resend flows sign before mail without an earlier durable write; password reset and invitation acceptance verify their token before changing account state. These paths retain their implementations. The original 35 replayed fork commits and all predecessor messages remain ancestors, including hierarchy, currentness, observations, history, presentation, origin confinement and brand pins.

## Qualification

The 17-case route/controller regression file uses real database repositories and migrations. On the original head, 12 missing/empty cases fail and five configured-key flows pass. After repair, it asserts controlled direct-action refusal before form reads or cookies, unchanged users and role memberships, pending subscriber status/OTP/methods, untouched OIDC profiles and role synchronization, and no invitation user reservation. Configured cases exercise successful signup/local-login sessions, including inferred development `ORIGIN`, subscriber tokens, OIDC provisioning/synchronization/session signing and invitation roles. Three additional common-controller cases check admission and the unchanged HMAC algorithm.

The executable code and regression bytes are bound to the corresponding working-tree files by SHA-256. The newly added state cases fail on the original implementation before repair; configured-key flows already pass. An initial type check identified the early form-result shape and test-event typing. Self-review also rejected an initial full-setup action guard because it would additionally restrict valid-key development actions; the final guard checks only the signing key, with a compatibility regression. These corrections precede final qualification and publication.

Final qualification uses one cached-base Playwright container for installation, tests, build and pruned runtime, plus disposable database/Redis resources. Installed dependencies measured about 482 MiB before pruning, then 383 MiB, and build output 38 MiB. Runtime networking is internal-only and no host port is published. No new image is built or published; earlier Debian-image and unchanged fork-wide evidence remain tied to their original cuts. A copy of the already installed formatter was used for final documentation formatting after pruning, avoiding another dependency installation.

The first HTTP probe exposed response negotiation: without an explicit HTML Accept header, SvelteKit serializes an action failure in an HTTP 200 JSON envelope. The final proof checks both representations and their persisted state. The first MariaDB runtime start raced database TCP readiness; startup logged migration/seed connection refusal before the fixture could query users. The server was stopped, the failed specimen preserved, and native TCP readiness established before the successful rerun. This evidence does not establish recovery from a database that is unavailable during application initialization; startup behavior was not changed by this repair.
